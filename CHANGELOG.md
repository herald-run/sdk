# Changelog

Client packages: `@herald-run/sdk`, `@herald-run/cli`, `@herald-run/mcp` and the `herald-run` Python package. Compatibility policy: https://herald.run/docs/api/.

## Unreleased

- Agents: presence states `working` (blue; use it while the agent works) and `error` (red) join `idle`, `blocked` and `offline`. `busy` is deprecated but still accepted by the SDK, CLI and MCP, and the viewer shows it as Working. The wire carries `working` as `busy` and `error` as `blocked` with `condition: 'error'`, so older viewers still list the agent (as Working or Blocked); the SDK maps them back on reading.
- Chat: `chat.setStatus(room, { state, text? } | null)` and `chat.status(room)` set, clear and read a room's one sealed status (idle, working, blocked, error; `busy` counts as working; text up to 120 characters). It replaces the last status, makes no message or unread, is listed by `chat.list()` as `status` and arrives live in `onRoom` as `{ room, status }`. Exported `ChatStatus`, `ChatStatusInput`, `ChatRoomStatus`. Writes are rate limited like messages; older clients show no status. A status that cannot be opened (after one key refresh) reaches `onRoom` as `status: null` and `onError`.
- Chat: `chat.wakes(handler, { onRoom })` receives a room's archive, restore and delete as `ChatRoomEvent` (`{ room, archivedAt }`, `null` once restored, or `{ room, deleted: true }`), live only, never replayed.
- Chat: `chat.archive(room)`, `chat.unarchive(room)` and `chat.deleteRoom(room)`; `ChatRoom.archivedAt` (ms, `null` while active). An archived room is read-only: sends, answers, edits, reactions, deletes and head changes fail with 409 `CHAT_ARCHIVED`, pending wakes end and open forms close as expired. A connection may delete only rooms it created (403 `NOT_CREATOR` otherwise).
- Agents: a profile's optional `details` (up to 12 `{ label, value }` entries, label 1 to 40 and value 1 to 200 characters, unique labels; exported `AgentDetail`, `agentDetailLimits`) lists facts an agent defines for its About section. Sealing refuses an invalid list; reading keeps the valid entries and the rest of the profile.
- Agents: a profile's optional `stoppable` lets people who may tag the agent (reach `all`) stop its current work; `chat.wakes(handler, { onStop })` receives each request as `ChatStop` (`room`, `subagent`, `by`), live only, never replayed.
- Chat (breaking): a connection takes part only through its registered agents. `chat.open(room)` opens a room by id; `chat.open(person | 'owner', { agent })` requires `agent` (`AGENT_REQUIRED` otherwise). `send`, `ask` and the other posts to a person or `owner` open the DM with `agent = sub`, and refuse without `sub`; `read`, `next` and `wait` do the same with `for`, which `wait` and `listen` also ack as, and `delete`, `attach` and `answer` with `sub`. `download` and `updateGroup` take a room id only. `chat.group(members, { agents })` requires `agents`: keys of this connection, or `{ connection, key, notify? }` for another connection's agent. `react`, `edit`, `title` and `answer` take `sub` too (`react`'s `remove` moves into `{ remove, sub }`); an answer's `sub` is the answering agent, and `group` titles as its own first agent. `chat.session()` and session rooms are gone.
- CLI (breaking): `herald chat send --as KEY` replaces `--sub` and is required for a person or `owner`; `chat react|edit|title|delete|answer` take `--as KEY`; `chat read|wait|listen` take `--for KEY` (needed for a person or `owner`); `--session` is gone; `chat group` takes repeatable `--agent KEY`. New `herald agents list|register|unregister` (`register KEY NAME` takes `--chat`, `--parent`, `--section A/B`, `--state`, `--task`, `--link`, `--ttl`, `--reach`).
- MCP (breaking): `chat_send` and `chat_ask` take `as` instead of `sub`, and `chat_react`, `chat_edit`, `chat_answer`, `chat_delete` and `chat_group` (for an existing room's title) take `as`; `chat_send` requires `as` for a person or `owner`, and `chat_wait` and `chat_read` `for`; `session` is gone; `chat_group` takes `agents`. New `agent_register`, `agent_unregister` and `agents_list`.
- Agents: `agents.register(key, profile, { ttl, reach })`, `renew`, `unregister` and `list` list a connection's agents; `setSubagent`, `renewSubagent`, `removeSubagent` and `subagents` stay as deprecated aliases, and `setPresence` still works but lists nothing. Profiles take an optional `section` (1 to 4 names, each up to 60 characters), `order`, `about` (up to 500), `requests` and `chat` (`'dm'` or `{ room }`; `register` joins that room). Exported `AgentProfile`, `AgentReach`, `AgentOptions`, `OwnAgent`, `agentEntryLimits`.
- Chat: rooms list their `agents` (`RoomAgent`: `connection`, `key`, `notify`, `context`, `reach`, `live`) and an agent DM its `agent`; the deprecated `subagents` field and the `RoomSubagent` type are gone. `chat.addAgent(room, key, { notify, context })` and `chat.removeAgent(room, key)` manage a connection's own room agents. Each room agent wakes by its own `notify` and by tags, and a tag still wakes it after it was unregistered unless its reach is `agents`.
- Chat: `send` seals `names` for its `sub` and `tags` keys (1 to 60 characters), filled from the agents this client registered; explicit entries win, and an invalid one is refused. Opened messages carry `names`; older clients ignore them.
- Chat: a socket still connecting after the keepalive interval is closed and retried instead of throwing.
- Agents: `register` joins an agent's `chat` room again after `unregister` or `chat.removeAgent`.
- Messages: `send` and `ask` take `as: key` (a registered agent) or `as: { key, name }`; the sender is sealed with its name, so it stays after the agent is unregistered. A malformed `as` is dropped on read and the message kept.
- Agents: presence and subagent profiles take an optional `task` and up to 8 `links` (`{ label, url }`, http or https; exported `AgentLink`, `agentLinkLimits`); a subagent profile's `parent` names another subagent key of the same connection (`subagentKey`). Link URLs may not contain credentials. Sealing refuses an invalid or repeated link URL, naming the link (`agentLinkError`); reading drops an invalid `task`, `parent` or link and keeps the rest of the profile. CLI `presence set`/`subagents set` take `--task` and repeatable `--link LABEL=URL` (split at the first `=` before `http://` or `https://`), `subagents set` takes `--parent`; MCP `presence_set` and `subagent_set` take the same fields. All are sealed; older clients ignore them.
- Messages: optional `room` (sealed) links a message or request to a chat room, so an app can offer to open it to a reader in that room; a malformed room is dropped on read and the message kept. CLI `send`/`ask --room`, MCP `send`/`ask` `room`; Python keyed clients validate it.
- Chat: each subagent has its own wake; `chat.ack(room, seq, subagent?)` settles one subagent's wake (without marking the room read), and `wakes()` leases and acks per subagent.
- Chat: `next()` and `wait` take the oldest wake of the connection or any of its subagents, and throw when the lease fails instead of waiting out the timeout. `ack` is one request and marks the room read. `wait` and `listen` read back what arrived while the socket was reconnecting. `list()` returns `ChatListing` (opened `title`, no chain); `ChatMessage.subagent` is gone (use `tags`), and `wakes()` reports a failed replay without a room.
- Chat: a hop is a turn passing to a different agent connection (a connection's own messages, subagents included, and humans-only messages never add one). Agents set `hopLimit` 1 to 1000 (default 6); only people turn it off. MCP `chat_group` takes `hopLimit` from 1, and with `room` adds or removes members and sets the title; CLI `chat group` takes `--hop-limit`. MCP `chat_wait` is no longer marked read-only.
- Threads: MCP `threads` and CLI `herald threads` take `before`/`--before` to continue past the first page; the CLI prints the thread id on every successful send, ask and wait.
- Chat: `chat.ask` (CLI `chat ask`) rejects a form the Inbox would not accept, such as an unknown field type, before sending.
- Threads: `threadKey` on `send` and `ask` names a conversation. Messages sent with the same key by one connection share a thread; the server stores only a keyed digest of the name (`threadDigest`). `threads()` (CLI `herald threads`, MCP `threads`) lists a connection's threads, by default those with a waiting request. MCP `send` returns `threadId`, and the CLI prints it on stderr. Exported `ThreadList`, `ThreadSummary`.
- Declining: a person can decline any pending request. The record ends as `cancelled` with `declined: true` and an optional end-to-end encrypted note (`decline.note`, verified like an answer, `ctx.t = "decline"`); `refuseLabel` (CLI `--refuse-label`) sets the decline button's label. MCP results include `declined` and `declineNote`.
- Live socket: a `read` event (`ReadEvent`) lists records the same member read on another device.
- Forms: an `annotations` field type for commenting on an attached PDF. It names the PDF in `attachmentId`, and its answer is a list of `{page, anchor, quote?, boxes?, text}`: a comment anchored to selected text (`quote`, one box per line), an image (one box) or a whole page (1-based page, boxes as page fractions); exported `annotationSchema`, `Annotation`, `AnnotationBox`. Python keyed clients accept it too.
- CLI: `send`/`ask --annotate PDF` attaches a PDF and adds a `comments` field; human output prints one comment per line. In `-i` input an annotations field may give a local `file`.
- SDKs: while the live socket is open, `wait` (and Python `watch`) falls back to polling every 5 minutes instead of 30 s (30 s while it is down); TypeScript `wait` checks only on sync events newer than the last one it saw, and a check that overlaps an event runs once more.
- CLI: `herald listen` flushes task logs every 10 s instead of 2 s; a task's final logs still flush before its completion update.
- SDKs: team workspaces. Keyed clients verify the workspace succession chain and signed roster (pinned with `pin`/`onPin`, Python `pin`/`on_pin`), seal to the team key (`team` on send), accept answers only from verified team members (`answeredBy`, `response.by`) and reseal once on `409 E2EE_STALE_KEY`. Requests send `X-Herald-Client: sdk/<version>`; `workspace` sets `Herald-Workspace`. New schemas for team routing policies, member availability and update pushes; `e2ee` adds the workspace functions and vectors.
- CLI: `herald login --workspace SLUG`, `send`/`ask --team SLUG`; `show` prints the team and who answered; `whoami` shows the workspace and its teams.
- Team workspaces: roster members carry a signed `name`; invite links carry `#<secret>.<fingerprint>` (`inviteFragment`, `parseInviteFragment`) and join proofs bind that fingerprint; key wraps verify only under the chain head; `recertifyWorkspace` re-signs a certificate verified under the previous roster with its teams intersected; `keyringPin` keeps workspace anchors in the personal keyring without root swaps or downgrades. Keyed clients take a record's team only from a verified envelope or their own send, and only within their certified teams. Env-token clients read a pin from `HERALD_PIN`; the CLI keeps one current with `--pin-file FILE`.
- TypeScript SDK: the live socket sends a keepalive `ping` every 30 s and reconnects when one goes unanswered, so a silently dropped connection no longer leaves `wait` on the 5-minute poll.

## 0.3.0-beta.6

- CLI: `herald login` waits out rate limits (which a login pending a few minutes reached) and bodiless server errors, honouring `Retry-After`, instead of failing with "Login failed."; other failures show the server's message.
- CLI: the README points Claude Code and Codex at the skills, which run the CLI.
- Forms: `questions` input (the shape of Claude Code's AskUserQuestion) becomes required choice fields `q1`…`qN`; `questionAnswers` maps answers back by question text, and `fieldAnswers` does so from a request's fields. Fields gain `header` and `other` (free text instead of a choice); options gain `description` and Markdown `preview`.
- MCP `ask` takes `questions` and returns `answers`, as do `wait` and `get_message` for its reply; CLI `-i` input takes `questions` (see `examples/questions.json`); Python keyed clients validate them alike.
- Compatibility: clients before this release reject replies with Other answers (they read them as not matching the request), so update clients before sending `questions` or `other`.
- Forms: `minLength` and `maxLength` count code points, like every other length limit; question texts must be unique.

## 0.3.0-beta.5

- CLI: `send`, `ask` and `register` reach every capability through flags, merged onto `-i` input: `--body-file`, `--kind`, `--field ID[?]:TYPE[:LABEL[:CHOICES]]` (including `secret` and `secret-file`), `--action`, `--block TYPE=PATH` (code, diff, json, table from CSV, image), `--review`, and for `register` `--target`, `--webhook`, `--description`, `--type`. In `-i` input, image blocks may give a local `file`.
- CLI: `ask`, `send --wait` and `wait` take `--out [FIELD=]PATH` to write secret and file answers to new private files without printing them; `send --secret-file PATH` offers a secret. `request-secret`, `request-file`, `send-secret` and `upload` are removed.
- CLI: `integrate` and the bundled skills are removed. Skills are at https://herald.run/skills; register the MCP server with the client's own command, e.g. `claude mcp add herald -- npx -y @herald-run/mcp`.
- CLI: `account` shows the account holder and a separate `connection` line; `whoami` shows one `account` line.

## 0.3.0-beta.4

- Content is always end-to-end encrypted; tokens without a key are refused. Connection tokens have the form `hdr_<auth>.<seed>.<fingerprint>` (from `herald login` or Settings → Connections); the SDKs encrypt what they send and decrypt what they read: messages, forms, answers, tasks, logs, results, files, secrets and secret offers. Only `hdr_<auth>` is sent to the server. If the account's keys are missing or do not match the token, content calls fail; nothing falls back to plaintext.
- SDKs: decrypted records carry `e2ee: true`; records this connection cannot decrypt carry `locked: true`, and unsealed or forged ones `unverified: true`, with their content withheld. Leading or trailing whitespace in a token is ignored. New `keys()`, `safetyCode()` / `safety_code()` for the 30-digit account safety code, `openTask()` / `open_task()` for webhook tasks, `deviceCertificate()`, and a required `certificate` on `createIntegration()`. Failed tasks may carry `reason` (`webhook-unavailable`, `not-acknowledged`, `lease-lapsed`). Uploads return the attachment with its file `key`; `download()` takes that attachment, or an ID of a file seen in an opened record. `revealSecrets()` takes no private key. The `keyed` getter is gone.
- CLI: `herald login` certifies a key for the device once you confirm that the account safety code matches the approval page (`--safety-code CODE` outside a terminal); open Herald on a signed-in device first to set up the account's keys. `whoami` and `status` show the safety code. `download` needs `--message ID`. `messages --search` and `search` filter the newest five decrypted pages locally, since the server cannot search encrypted content. Older logins without a key must log in again.
- MCP: uses keyed CLI logins; `download_file` needs the `messageId` of the message holding the file.
- Secret file fields: `{type: "file", secret: true}` (JSON Schema `x-herald-type: secret-file`) send the uploads to the asking connection only, like secrets; Herald deletes them 15 minutes after the answer. `revealSecrets()` / `reveal_secrets()` return their attachments, ready for `download()`. CLI `request-file --out PATH` and MCP `request_file` write one requested file to a new 0600 file and print only the ID and status, refusing answers from apps that would keep the file in history; the `herald-get-file` skill uses them.

## 0.3.0-beta.1

- Published as `@herald-run/sdk`, `@herald-run/cli` (`npx @herald-run/cli`) and `herald-run` (import `herald`); Node.js 20+, Python 3.11+.
- CLI: human-readable output by default and `--json` for machine output; the input file flag is now `--input`/`-i` (was `--json`). Exit codes: 0 answered, 1 error, 2 usage, 3 expired, 4 cancelled.
- CLI: `--version`, `help <command>`, `completion`, `whoami`, `status`, `messages`/`search`, `show`, `wait`, `logs`, `download`, `account`, `destinations update|remove|rotate-secret`, `send --file`, profiles (`--profile`, `HERALD_PROFILE`), `logout` revokes the token, `login` opens the browser and asks no scope question, `listen --target KEY` finds the destination.
- SDKs: `HeraldError.code`, `User-Agent`, `ping`, `token`/`revokeToken`, `account`, `taskLogs`, `download`, `rotateDestinationSecret`. Python adds `create_keys`, `seal`/`unseal`, `reveal_secrets`, `verify_webhook` and the synchronous `SyncHerald`.
- `@herald-run/mcp`: MCP server (`herald-mcp`, stdio) with send, ask, wait, message, thread, file and secret tools; secrets are written to 0600 files, never returned.
- CLI: `integrate claude-code|codex [--scope user|project] [--dry-run]` installs Herald skills and registers the MCP server; idempotent.
- Docs at https://herald.run/docs with an OpenAPI 3.1 description at `/docs/openapi.json`, generated from the schemas in `@herald-run/sdk/schema`.
